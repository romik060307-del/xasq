# OHLI Social v3.6.5 — rencana pengujian

Dokumen ini memisahkan pemeriksaan source yang sudah dijalankan dari pengujian manual yang masih harus dilakukan pada perangkat.

## Hasil yang sudah dijalankan

- `node tools/source-verify.mjs`: 125 pemeriksaan statis lulus.
- Pemeriksaan meliputi parsing JavaScript inline, keseimbangan blok CSS, kontrak endpoint Chat/teman/LIVE, aksi media, alur signaling, polling, identitas build dan workflow.
- APK tidak dibangun pada lingkungan ini. Gradle wrapper dan Android SDK tidak tersedia.
- Tes runtime dua akun dan WebRTC lintas perangkat belum dijalankan.

## 1. Chat — download dan hapus media

Gunakan dua akun uji pada dua browser/perangkat.

1. Akun A kirim foto, voice note, video, dan file yang didukung kepada B.
2. Pada akun B, buka menu aksi setiap pesan dan pilih **Unduh media**. Pastikan file tersimpan dan dapat dibuka.
3. Pada akun B, pilih **Hapus dari chat saya**. Pastikan pesan hilang di B, tetapi tetap terlihat di A.
4. Kirim media lain dari A. Pada A pilih **Hapus untuk semua**. Pastikan pesan hilang di kedua akun.
5. Ulangi dengan media sekali lihat. Pastikan tidak ada aksi unduh dan akses tetap mengikuti mekanisme sekali lihat yang sudah ada.
6. Uji pada Safari iOS dan Chrome Android karena browser dapat mempunyai perilaku berbeda saat mengunduh Blob.

## 2. Chat — posisi pesan terbaru

1. Buka percakapan dengan A dan gulir ke beberapa pesan lama.
2. Kirim pesan baru dari B. Pastikan tampilan kembali ke bagian paling bawah setelah pesan tampil.
3. Biarkan A mengirim pesan ketika B sedang berada di bagian paling bawah. Pastikan pesan baru terlihat.
4. Gulir B ke atas ketika A mengirim pesan. Pastikan pembacaan riwayat lama tidak memaksa scroll ke bawah.
5. Uji saat lampiran gambar/video masih memuat agar layout akhir tetap mengikuti pesan terbaru.

## 3. LIVE — undang teman dan permintaan tampil

Gunakan akun Host A, teman B, dan penonton C. Gunakan HTTPS/localhost dan browser yang mendukung WebRTC.

1. A memulai LIVE publik. Pastikan kamera dan mikrofon hanya aktif setelah Host memberi izin.
2. A membuka **Undang**. Pastikan daftar berasal dari teman OHLI, bukan seluruh kontak telepon.
3. A mengundang B. B harus menerima atau menolak undangan; menolak tidak boleh memasukkan B ke ruang LIVE.
4. B menerima undangan dan masuk sebagai penonton. A harus melihat permintaan B untuk tampil dan dapat menerima/menolak.
5. Saat A menerima, B tetap perlu menekan **Kamera & mikrofon** dan menyetujui permission browser. Pastikan B baru muncul sebagai peserta setelah tahap ini.
6. C menonton LIVE dan menekan **Minta bergabung**. A menerima atau menolak; bila diterima, C harus mengaktifkan kamera/mikrofon secara eksplisit.
7. Pastikan semua tile menunjukkan nama peserta, avatar ketika kamera mati, dan indikator **Mic mati** ketika mikrofon dinonaktifkan.
8. Uji dua, tiga, dan empat peserta di panggung. Batas ini menghitung Host sebagai satu peserta.
9. Peserta B menekan **Keluar panggung**. Pastikan kamera/mikrofon B berhenti, B menjadi penonton, dan LIVE A serta peserta lainnya tidak terputus.
10. Host A mengakhiri LIVE. Pastikan semua perangkat memperoleh status LIVE berakhir.
11. Uji LIVE privat: penerima undangan yang menerima harus dapat menonton; akun yang tidak diundang tidak boleh dapat membuka siaran.
12. Uji tolak lalu kirim permintaan ulang; server harus menerapkan jeda 30 detik.

## 4. LIVE — keterbatasan koneksi

- Koneksi memakai WebRTC P2P mesh dengan STUN publik. NAT carrier, firewall, VPN, atau router dapat menghalangi koneksi langsung.
- Jika perangkat berada pada jaringan berbeda dan koneksi gagal, catat browser, tipe jaringan, status ICE/connection state, dan log server. Untuk reliabilitas lintas NAT diperlukan layanan TURN.
- P2P mesh mengirim stream per peserta ke peserta lain; penggunaan publik berskala besar perlu SFU. Jangan menaikkan batas penonton hanya dengan mengubah angka UI.
- Random LIVE Match belum termasuk versi ini.

## 5. Pengukuran performa server

Ukur pada kondisi yang sama sebelum dan sesudah memasang source:

- Waktu login, membuka daftar chat, membuka percakapan dengan riwayat besar, dan mengirim pesan.
- Waktu respons API p50/p95, request per menit, ukuran payload, error rate, CPU/RAM server host, dan waktu penulisan file JSON.
- Uji 2, 5, lalu 10 klien secara bertahap. Hentikan bila CPU, RAM, antrean, atau error meningkat tajam.
- Bandingkan akses lokal melalui LAN dengan akses melalui Cloudflare Tunnel. Pastikan perangkat host tidak masuk mode hemat daya dan server Android tetap berjalan.
- Jangan menyebut server “tanpa batas”. Source masih memakai JSON file dan lock global sehingga akan ada batas CPU, memori, storage, dan throughput.

## 6. Pemeriksaan regresi fitur lama

- Login/register dan refresh sesi.
- Feed, Story, profil, notifikasi, Follow, Teman, Chat teks, voice note, lampiran, panggilan, grup, Channel, koleksi audio dan stiker.
- Pastikan file media atau pesan biasa tidak ikut terhapus ketika menghapus pesan lain.
- Pastikan logout dan login kembali tidak merusak data.
